17. 실습 파이프라인과 CRAG 평가 — 코드의 입력·상태·채점을 연결하기

이 장은 원본 실습 type1/type2의 공통6개 노트북, 보조 코드, 실습 PDF 두 개를 대조한 학습 교안이다. 실행 환경·실측 성능을 새로 검증했다고 주장하지 않는다. 외부 계정·API key·DB·서버·모델을 켜지 않아도 아래의 데이터 흐름과 작은 계산은 학습할 수 있다. 자격증명은 포함하지 않는다.

1. Query Engine은 모델·벡터 DB와 같은 객체가 아니다

1. Llama_index.ipynb는 다음 단계를 분리한다.

원본 Document → 파서/청킹 → 출처가 있는 Node
             → 문서 임베딩 → vector store + 본문/메타데이터
질문 → 질의 임베딩 → Retriever → 점수 있는 Node 목록
     → Response Synthesizer → 답/요약 + source_nodes

Query Engine은 검색과 응답 합성을 연결하는 인터페이스다. index는 표현과 검색 구조, retriever는 후보 검색, synthesizer는 근거를 읽고 답/요약을 만드는 역할이다. 실습의 로컬 memory vector store도 외부 관리형 벡터 DB와 동일한 운영 기능을 자동 제공하지 않는다. index.as_query_engine()처럼 편의 API를 쓰더라도 내부 단계가 사라지지는 않는다.

CustomQueryEngine의 custom_query(query_str)는 retriever에서 nodes를 얻고 response_synthesizer.synthesize(query_str,nodes)에 연결할 수 있다. 반환을 단순 문자열로 바꾸면 출처 목록·점수·구조 정보가 사라질 수 있으므로 답과 source_nodes를 함께 추적한다. summary를 잘 만든 것과 원질문에 직접 답한 것은 다르며 목적에 맞게 프롬프트·합성 모드를 정한다.

2. Insert·update·refresh·delete는 무엇을 갱신하는가

동작 논리 입력 확인할 상태
insert 새 document ID·본문·metadata 새 nodes·벡터·본문 저장·참조 관계 추가
update 같은 ID의 새 버전 예전 nodes·표현 제거/교체, 버전 일치
refresh 여러 document의 현재 상태 변경 감지·해시 규약에 맞는 선택적 갱신
delete document ID 또는 node IDs 검색 표현·본문·참조·캐시의 잔존 여부

원문을 바꾼 뒤 벡터·본문·query engine/caches가 이전 상태를 읽으면 최신 답이 반영되지 않을 수 있다. update/refresh의 정확한 API 이름과 반환은 설치된 LlamaIndex 버전의 계약을 따른다. 실습은 같은 질문을 갱신 전후에 다시 보내 변화를 살피지만, 생성 응답 변화만으로 인덱스 정합성을 증명하지 않는다. ID·node 수·본문/metadata 버전·검색 결과를 함께 확인해야 한다. 이는 원본 실습 PDF 20~22쪽의 DB management 흐름이다.

2. RAG.ipynb는 도시 Wikipedia 자료를 청크로 만들고 Retriever→Generator를 직접 연결한다. 청크 크기·Top-K·응답 프롬프트를 바꾸면 회수 근거와 최종 응답이 함께 바뀔 수 있다. 한 번에 하나의 조건을 바꾸고 질문별 근거·답변을 저장해야 원인을 구분한다. 자료 밖 질문에 모델이 답했다고 검색 근거가 충분한 것은 아니다.

3. CRAG 데이터와 세 과제

여기서 CRAG는 Comprehensive RAG Benchmark라는 평가 자료다. 11장의 Corrective RAG 기법명과 구별한다. 실습 Graph RAG PDF14~22쪽은 다섯 분야(finance/sports/music/movie/open), static·slow/fast-changing·real-time의 변화 속도, head/torso/tail 개체의 빈도 차이, 단순 사실·조건·집합·비교·집계·multi-hop·후처리·false-premise 질문을 소개한다. 특정 판본의 표본 수를 현재 전체 규모로 일반화하지 않는다.

데이터 필드/구성 역할 확인할 문제
interaction_id 질문의 고유 식별 여러 구성의 같은 질문 비교
query 사용자 정보 요구 조건·범위·비교 기준 보존
query_time 상대 시점의 기준 “현재/어제”를 모델 실행일로 임의 해석하지 않음
answer 및 대안 정답 reference 표기 변형·빈 정답·false premise 규약
search_results 검색된 웹 결과·HTML·자료 시각 title/본문/출처/시간을 파싱·보존
domain·question_type 등 평가 층화 질문 유형별 누락·어려운 사례 비율

세 task는 제공 근거의 조건을 달리한다. 실습 PDF20쪽의 표에서 Task1은 웹 검색 결과5개, Task2는 같은5개와 mock KG/API, Task3는 웹 검색 결과50개와 mock KG/API를 사용하는 설정이다. 이는 제공되는 외부 자원 차이이며 다른 조건의 점수를 같은 설정처럼 비교하지 않는다. “mock” API도 호출 구조는 실제 외부 도구이며 값은 벤치마크용 고정 지식이다.

4. 전처리→웹 RAG→KG 결합

1. Data_preprocessing.ipynb는 bz2 JSONL 레코드·분포를 읽고 검색 결과 HTML을 텍스트로 파싱·분할한다. <script>, 메뉴, 빈 본문 등 노이즈를 제거하더라도 숫자·표 헤더·날짜·부정·출처를 없애지 않아야 한다. 질문별 웹 자료를 섞으면 원래 근거 범위가 달라지고 평가 누출이 생길 수 있다.

2. Task_1.ipynb는 Chunk Extractor→Retriever→Reader→RAG의 역할을 나눈다. 질문과 chunk 표현의 내적/cosine으로 Top-K를 고르고 Reader에 근거를 전달한다. 반환은 답뿐 아니라 검색 문서·source·설정도 남겨야 검색 누락과 생성 오류를 분리할 수 있다.

3. Task_2.ipynb의 KGQueryEngine은 LLM이 domain·entity·API 인자를 만들고 분기 코드/결정 트리가 mock API를 호출한다. 웹 검색 근거와 KG 응답을 합쳐 Reader에 전달한다. 이것은 SPARQL/Cypher 문자열을 임의 생성해 DB에 직접 보내는 것과 다른 구현이다. 회사명→ticker→지표 조회 같은 의존 호출이 있어 첫 entity 오류가 뒤 단계에 전파된다. KG 결과가 길면 본문을 전부 붙이는 대신 질문의 시점·지표·필드와 예산에 맞춰 선택해야 한다.

금융 finance_MCP.py는 회사명/ticker 일치 확인, 회사 후보, ticker 변환, 일·분 단위 가격 이력, 배당, 시가총액, EPS, PER, 회사 정보 Tool을 제공한다. metadata://finance-company-format Resource는 이름/ticker 형식 예시다. 일 단위와 분 단위 가격·거래량은 같은 집계값이라고 가정하지 않는다. 응답의 자료 시각·타임존·snapshot을 query_time과 대조한다. 이는 금융 투자 판단이 아니라 도구 입력·단위 학습이다.

5. 네 등급과 점수의 분모

원본 평가 노트북은 perfect=1, acceptable=0.5, missing=0, incorrect=−1이라는 네 판정을 사용한다. perfect/acceptable/incorrect/missing은 서로 배타적인 한 질문의 라벨이다. 각 개수를 P,A,M,I라 하면

$$S=P+0.5A-I,\qquad \bar S=\frac{P+0.5A-I}{N},\quad N=P+A+M+I.$$

예를 들어10질문에서 P4·A2·M3·I1이면 합점4, 질문당0.4다. 무조건 답하다 틀린 한 건을 적절히 보류하면 I가1 줄고 M이1 늘어 질문당0.1 오른다. 그렇다고 전부 보류하면 평균0이므로 유용한 답변 성능까지 좋다고 할 수 없다. answerable/null 유형별로 올바른 답·거절을 나눠 본다.

원본 PDF22쪽의 “Exact Accuracy”는 완전 정답 범주, “Accuracy”는 비완전이지만 의미가 맞는 범주로 정의해 가중한다. 이것을 문자열 exact match나 모든 correct를 합한 일반 accuracy와 혼합하지 않는다. 부분 정답을 포함한 다른 교안 사례의 (correct+0.5×partial)/N은 incorrect의−1 벌점이 없어 같은 점수식이 아니다.

LLM 판정기는 질문·prediction·대안 정답을 보고 라벨을 만든다. 판정 파싱 실패·timeout·모델 오류는 의미적 incorrect와 다르다. 원본 초기 코드의 단순 나머지=hallucinate 집계나 후속 코드의 inference 예외→missing 매핑은 각각의 구현 정책이다. 학습용 평가에서는 평가 성공 문항의 점수와 실패 수·가용성을 따로 보고한다. 실패를 조용히 평균 분모에서 빼거나 올바른 거절로 가장하지 않는다.

6. 같은 평가자로 비교하는 L0~L4

4_RAG_framework_evaluation_with_MCP.ipynb의 단계적 비교는 이름보다 변경 내용을 읽는다.

구성 바꾼 것 비교에서 고정할 것
L0 모델 단독 응답 질문·판정·샘플
L1 웹 RAG 자료·Top-K·Reader 예산
L2 검색/답변 후 self-verify 구조 verifier 기준·추가 호출
L3 plan→act→read→verify의 제한 반복 최대 반복·누적 근거·재시도·호출/토큰 예산
MCP 결합 구성 Tool 선택·호출과 KG 결과 연결 같은 query_time·출력 크기·평가셋

원본 LLMCallCounter는 추론 비용과 judge 비용을 분리하려고 호출·토큰을 센다. 코드가 별도 측정하지 않은 모델/도구 호출이 있으면 총 비용 추정에 누락될 수 있다. 반복 구조가 더 잘 나왔다고 구조 자체의 효과가 확인된 것은 아니다. 같은 예산으로 단일 RAG를 여러 번 실행해 투표하는 self-consistency 같은 대조군, 같은 참조 길이·질문, 실패·지연·비용 기록이 필요하다. 원본 노트북의 “What This Experiment Cannot Show”도 이 차이를 명시한다.

Self-verifier의 자신감은 사실 참 확률이 아니다. 최대 단계에 도달해도 미확인 사실을 추측하도록 강요하지 않는다. 새 검색이 실제로 새로운 근거를 추가했는지, 같은 질의만 반복했는지, claim–evidence가 맞는지 확인한다.

7. type1/type2의 핵심과 환경 차이

로컬 type1은 Conda/Jupyter와 설정한 외부 KG 주소를, Colab type2는 Drive 경로·subset·로컬 mock 서버 준비를 사용한다. 여섯 노트북의 핵심 학습 흐름은 겹치지만 설치 패키지·주소·도시 목록·데이터 판본·예제 인덱스·MCP 준비가 다르다. type2를 축약되어 다른 알고리즘이라고 단정하지 않는다. type1의 생성자 server 인자가 실제 주소 선택에 반영되는지 등 코드가 정말 사용하는 값을 확인한다. 실행 성공 여부는 이번 정적 교안 대조로 보장하지 않는다.

Notebook의 YOUR CODE HERE 표식과 실제 미완성 여부도 다르다. 이미 채워진 셀이라도 입력·출력·상태를 읽어야 하며 현재 웹 교안은 시험 문제/정답 파일을 바꾸지 않는다. 서버·환경 명령은 실행 전제 자료이고 이 페이지의 계산 시각화가 실제 외부 실행을 대신했다고 주장하지 않는다.

8. 확인 질문과 해설

  1. Query Engine을 사용하면 retriever와 synthesizer의 구분이 없어지는가?
  2. 문서 본문만 수정하면 인덱스의 모든 이전 표현도 자동 제거되는가?
  3. query_time이2024년인데 실행일이2026년이면 “현재 가격”을 어느 시점에 맞춰야 하는가?
  4. P4,A2,M3,I1의10문항 점수 합과 질문당 점수는?
  5. L3가 L1보다 높으면 agent 구조가 원인이라고 확정할 수 있는가?
  6. 평가 timeout을 전부 incorrect 또는 성공한 missing으로 바꿔도 되는가?
해설
  1. 아니다. 인터페이스가 연결할 뿐 검색·생성의 데이터와 역할은 분리된다.
  2. 보장되지 않는다. ID·본문·node·벡터·metadata·캐시·engine의 갱신 계약을 확인해야 한다.
